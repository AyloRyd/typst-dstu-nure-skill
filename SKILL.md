# Правила оформлення звітів у Typst (ДСТУ ХНУРЕ)

Цей скілл призначений для створення академічних звітів у форматі Typst з
використанням Typst-пакета ХНУРЕ `nure` та дотримання стандартів ДСТУ.

## 0. Вибір шаблону

Пакет `nure` існує у двох несумісних варіантах:

| Шаблон | Версія | Імпорт | Підхід |
| --- | --- | --- | --- |
| **pencelheimer** (типовий) | 0.2.x | `@local/nure:0.2.0` | конструктор: `style.dstu` + `config.setup` + блоки `parts.*` |
| linerds | 0.1.x | `@local/nure:0.1.1` | одна обгортка `pz-lb` / `coursework` / `coursework-v2` з усіма аргументами |

Правило вибору — НЕ питайте користувача:

- завжди використовуйте **pencelheimer**;
- linerds — лише тоді, коли користувач прямо про це попросив (згадав linerds,
  `pz-lb` або версію 0.1.x);
- виняток: якщо редагується вже наявний звіт, який імпортує `@local/nure:0.1.x`
  або викликає `pz-lb`, лишайтеся на linerds — інакше звіт перестане
  компілюватися.

Версії в імпортах вище актуальні на момент написання. Справжню версію беріть з
поля `version` у `vendor/<шаблон>/typst.toml`.

## Перед початком роботи

Повні клони обох репозиторіїв лежать у `vendor/` як git-підмодулі, тому їх
можна досліджувати навіть без інтернету. Оновлює їх щотижнева GitHub Action
(`.github/workflows/update-vendor.yml`), тож самі нічого не тягніть з
першоджерел і нічого не пуште.

1. Перевірте, що підмодулі ініціалізовані:

   ```bash
   git -C <тека скіла> submodule status
   ```

   Якщо рядок починається з `-`, підмодуль порожній — ініціалізуйте:

   ```bash
   git -C <тека скіла> submodule update --init
   ```

2. Перевірте, що пакет потрібної версії встановлено для Typst:
   `~/.local/share/typst/packages/local/nure/<version>/`. Якщо теки немає,
   підключіть клон симлінком (і скажіть про це користувачеві):

   ```bash
   ln -s <тека скіла>/vendor/pencelheimer ~/.local/share/typst/packages/local/nure/0.2.0
   ```

## Де шукати деталі API

Інформацію про API звіряйте з `vendor/`, а не з пам'яті — шаблони відрізняються
навіть назвами аргументів.

**pencelheimer** (`vendor/pencelheimer/`):

- `README.md` — архітектура та швидкий старт;
- `src/config.typ` — `config.setup(...)` з doc-коментарями до кожного
  аргументу, словники освітніх програм і дисциплін (`subject: "АПЗ"`
  розгортається в повну назву);
- `src/parts.typ` — структурні блоки: `report-title-page`,
  `coursework-title-page`, `title-heading`, `task-list`, `calendar-plan`,
  `abstract`, `table-of-contents`, `metadata`;
- `src/style.typ` — `style.dstu` (show-правило, аргументи `skip`, `offset`),
  `style.appendices`, `style.spacing`, `style.dstu-table` (таблиці з
  «Продовження таблиці» за ДСТУ);
- `src/utils.typ` — `nheading`, `hfill`, `uline`, `bold`, `img`;
- `template/main.typ` — стартовий кістяк звіту.

**linerds** (`vendor/linerds/`):

- `README.md` — шаблони `pz-lb`, `coursework`, `coursework-v2`, утиліти,
  метадані в `doc.toml`, бібліографія `bibl.yml`;
- `src/lib.typ` — сигнатури шаблонів із doc-коментарями;
- `template/default/` — кістяки `lab.typ`, `coursework.typ`,
  `coursework-v2.typ` та помічник `utils.typ`.
- Увага: розділ про встановлення під Windows у README наводить функцію
  `nure-report` з аргументами `discipline`/`author`/`supervisor` — такої
  функції в пакеті немає. Користуйтеся `pz-lb` з `authors:`/`mentors:`/`subject:`.

Еталонні повні звіти з додатками та лістингами коду — по одному на шаблон:
`examples/pencelheimer/example-pz.typ` і `examples/linerds/example-pz.typ`.
Тіло в них однакове, відрізняється лише налаштування документа.

## 1. Ініціалізація та налаштування документа

### pencelheimer (типово)

```typst
#import "@local/nure:0.2.0": config, parts, style

#show: style.dstu.with(skip: 1) // титульна сторінка без номера

#config.setup(
  title: "Назва роботи",
  subject: "АПЗ",
  work-type: "ПЗ", // або "ЛБ", "КР", "РФ", "ІДЗ"
  work-number: 2,
  edu-program: "ПЗПІ",
  mentors: (
    (name: "Петренко П. П.", degree: "ст. викладач кафедри ПІ", gender: "m"), // m - чоловік, f - жінка
  ),
  authors: (
    (name: "Іваненко І. І.", edu-program: "ПЗПІ", group: "XX-X", gender: "m", variant: none),
  ),
)

#parts.metadata()
#parts.report-title-page()
#parts.title-heading() // заголовок з назвою роботи; пропустіть, якщо не потрібен
#v(-style.spacing)
```

Аргументи `parts.*` за замовчуванням беруться з `config.setup`, але кожен можна
перевизначити у виклику блока.

### linerds

Для ПЗ та ЛБ використовується шаблон `pz-lb`. Усі аргументи мають формат `kebab-case`.

```typst
#import "@local/nure:0.1.1": pz-lb, style

#show: pz-lb.with(
  title: "Назва роботи",
  subject: "АПЗ",
  layout: "ХНУРЕ",
  type: "ПЗ", // або "ЛБ"
  number: 2,
  edu-program: "ПЗПІ",
  university: "ХНУРЕ",
  mentors: (
    (name: "Петренко П. П.", degree: "ст. викладач кафедри ПІ", gender: "m"), // m - чоловік, f - жінка
  ),
  authors: (
    (name: "Іваненко І. І.", edu-program: "ПЗПІ", group: "XX-X", gender: "m", variant: none),
  ),
)
```

Далі правила спільні для обох шаблонів: обидва експортують модуль `style` з
`style.spacing` і `style.appendices`.

## 2. Стилістика тексту та граматика (Безособовий стиль)

В академічних звітах суворо заборонено використовувати першу особу ("я зробив", "ми дослідили"). Текст має бути написаний у безособовій формі або пасивному стані:

- **Неправильно:** Я відкрив вікно та виділив задачі.
- **Правильно:** Було відкрито вікно та виділено задачі.
- **Неправильно:** Під час роботи я навчився створювати зв'язки.
- **Правильно:** Під час виконання роботи було отримано навички створення зв'язків (або "було розглянуто як створювати зв'язки").

Також уникайте надлишкового форматування (наприклад, жирного тексту `*жирний*`), якщо цього не вимагає структура документа.

## 3. Списки та пунктуація

Списки мають суворо відповідати правилам оформлення:

1. Речення перед списком закінчується двокрапкою (`:`).
2. Перша літера після двокрапки (в тому числі на початку кожного елемента списку) має бути **малою** (за винятком абревіатур чи власних назв типу `Google`, `Start-to-Finish`).
3. Між елементами списку ставиться крапка з комою (`;`).
4. Після останнього елемента ставиться крапка (`.`).

**Приклад:**

```typst
Для гнучкого планування було застосовано типи зв'язків:
- затримка (Delay): встановлена між задачами;
- випередження (Lead): дозволяє розпочати реалізацію раніше;
- інші типи зв'язків: використовуються за потреби.
```

## 4. Заголовки та інтервали

- **Не пишіть цифри в заголовках вручну!** Шаблон Typst автоматично генерує нумерацію для заголовків 1-го (`=`), 2-го (`==`) та 3-го (`===`) рівнів.
  - **Неправильно:** `=== 1. Формування послідовностей`
  - **Правильно:** `=== Формування послідовностей`
- Використовуйте змінну `style.spacing` для усунення зайвих відступів перед текстом після заголовку: `#v(-style.spacing)`

## 5. Робота із зображеннями (Скріншоти)

Для вставки зображень стандартним методом використовуйте блок `#figure`:

```typst
#figure(
  image("img/project.png"),
  caption: "Скріншот вікна задач проєкту зі встановленими зв'язками",
)
```

### Плейсхолдер, коли зображення ще немає

Якщо за змістом потрібен рисунок, але самого файлу зображення немає (скріншот
ще не зроблено, користувач не надав його), НЕ пропускайте рисунок і НЕ
вигадуйте шлях до неіснуючого файлу — вставте плейсхолдер: світло-сірий
прямокутник, усередині якого той самий текст, що й у підписі знизу.

Оголосіть помічник один раз після налаштування документа:

```typst
#let placeholder(caption, height: 6cm) = figure(
  rect(
    width: 100%,
    height: height,
    fill: luma(230),
    stroke: 0.5pt + luma(170),
    inset: 1em,
  )[
    #set align(center + horizon)
    #text(fill: luma(90), caption)
  ],
  caption: caption,
)
```

Далі використовуйте його замість `#figure(image(...))`:

```typst
#placeholder("Скріншот вікна задач проєкту зі встановленими зв'язками")
#placeholder("Діаграма компонентів системи", height: 8cm)
```

Нумерація («Рисунок 1.1 – ...») та посилання працюють так само, як для
звичайного `#figure`. Коли з'явиться справжній файл, достатньо замінити виклик
`placeholder(...)` на `#figure(image(...), caption: ...)` з тим самим підписом.

Обов'язково повідомте користувачеві перелік плейсхолдерів, які було вставлено,
щоб він знав, які скріншоти треба доробити перед здачею.

## 6. Оформлення додатків (Appendices)

Усі додатки (програмний код, результати роботи, скріншоти презентації, посилання на відео) мають йти в кінці документа.
Перед першим додатком ОБОВ'ЯЗКОВО використовується правило `#show: style.appendices`, яке змінює формат заголовків на "Додаток А", "Додаток Б" тощо. Усі заголовки додатків позначаються одним знаком `=`.

**Приклад оформлення розділу додатків:**

```typst
#show: style.appendices

= Відеозапис
Відеозапис презентації: https://youtu.be/...
Хронологічний опис:
00:00 Вступ
01:30 Основна частина

= Слайди презентації
#for i in range(8) {
  figure(image("prez.pdf", page: i + 1), caption: "Слайд " + str(i + 1))
}
```

## 7. Програмний код

Для вставки коду використовується стандартний Markdown-синтаксис із вказанням
мови (наприклад, ` ```typescript `). Номери рядків НЕ пишіть у самому коді
вручну — вони заважають копіювати код і збиваються після правок. Натомість
один раз після налаштування документа додайте правило, яке нумерує рядки
автоматично (блоки без мови, як-от дерева каталогів, лишаються без номерів):

```typst
#show raw.where(block: true): it => {
  if it.lang == none { return it }
  show raw.line: line => {
    box(width: 1.5em, align(right, str(line.number)))
    h(0.75em)
    line.body
  }
  it
}
```

**Приклад коду в додатку:**

````typst
= Приклади програмного коду
== Запит до API <api-code-ref>
```typescript
const API_KEY = "SECRET";

const url = new URL("https://example.com/api");
url.search = new URLSearchParams({ key: API_KEY }).toString();
```
````
