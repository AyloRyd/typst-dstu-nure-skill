# Шаблони пакета `nure`

Це довідник із підключення та використання самого пакета. Правила оформлення
тексту (стиль, списки, рисунки, додатки, код) описано в `SKILL.md`, вони
однакові для всіх шаблонів.

## Які шаблони є

Пакет `nure` існує у трьох несумісних між собою варіантах. Усі вони лежать у
`vendor/` як git-підмодулі:

| Шаблон | Версія | Імпорт | Документація |
| --- | --- | --- | --- |
| **linerds** (типовий) | 0.3.x | `@local/nure:0.3.0` | `vendor/linerds/README.md`, `vendor/linerds/docs/` |
| pencelheimer | 0.2.x | `@local/nure:0.2.0` | `vendor/pencelheimer/README.md`, doc-коментарі в `src/` |
| linerds_old (застарілий) | 0.1.x | `@local/nure:0.1.1` | `vendor/linerds_old/README.md`, doc-коментарі в `src/lib.typ` |

Новий звіт завжди пишіть на **linerds** (`0.3.x`), користувача про шаблон
не питайте.

Якщо користувач називає функцію, якої в linerds немає (`config.setup`,
`parts.*`, `pz-lb` з аргументами 0.1.x тощо), скажіть, що в поточному шаблоні
її немає, у якому шаблоні вона є, і чим її замінити в linerds. Не
перемикайтеся через це на інший шаблон.

Якщо редагується вже наявний звіт на іншому шаблоні (pencelheimer,
linerds_old чи взагалі власна версія пакета), то ПЕРЕД будь-якими правками
запропонуйте мігрувати його на linerds і поясніть, що це означає:

- потрібен Typst 0.15 або новіший, тож Typst, можливо, доведеться оновити, а
  звіти на старих шаблонах після цього можуть перестати компілюватися;
- зміниться налаштування документа (імпорт, `work(...)`, титулка) і, можливо,
  окремі виклики (`img` → `fig`, `hfill`, власні утиліти);
- титулка й оформлення можуть трохи змінитися, бо linerds точніше
  відповідає ДСТУ 3008:2015.

Лише якщо користувач прямо скаже лишитися на поточному шаблоні, редагуйте
звіт на ньому (API — у `vendor/<шаблон>/`). Інакше мігруйте.

Справжню версію для імпорту беріть з поля `version` у
`vendor/<шаблон>/typst.toml`. Інформацію про API звіряйте з `vendor/`, а не з
пам'яті: шаблони відрізняються навіть назвами аргументів.

Еталонний повний звіт з додатками й лістингами є для кожного шаблону:
`examples/<шаблон>/example-pz.typ`. Тіло в них однакове, відрізняється
налаштування документа, а приклад `linerds` додатково показує його можливості:
`fig` з власною схемою (`examples/linerds/img/`), `tab` з приміткою, `note`,
пронумеровану формулу з поясненням через `utils.noindent` і лістинг у `figure`
з підписом.

## Перед початком роботи

Підмодулі оновлює щотижнева GitHub Action
(`.github/workflows/update-vendor.yml`), тому самі нічого не тягніть з
першоджерел і нічого не пуште.

1. Перевірте, що підмодулі ініціалізовані:

   ```bash
   git -C <тека скіла> submodule status
   ```

   Якщо рядок починається з `-`, підмодуль порожній — ініціалізуйте:

   ```bash
   git -C <тека скіла> submodule update --init
   ```

2. Перевірте, що пакет потрібної версії встановлено для Typst:
   `~/.local/share/typst/packages/local/nure/<version>/` (на macOS —
   `~/Library/Application Support/typst/packages/local/nure/<version>/`). Якщо
   теки немає, підключіть клон симлінком і скажіть про це користувачеві:

   ```bash
   mkdir -p ~/.local/share/typst/packages/local/nure
   ln -s <тека скіла>/vendor/linerds ~/.local/share/typst/packages/local/nure/0.3.0
   ```

3. `linerds` (`0.3.x`) потребує **Typst 0.15 або новішого**
   (`typst --version`). Якщо версія старіша, скажіть про це користувачеві —
   не перемикайтеся мовчки на інший шаблон.

4. Якщо щось не працює так, як описано тут (Typst не знаходить пакет,
   симлінк веде на теку, якої немає, у `vendor/` немає очікуваного шаблону,
   функції з цих інструкцій немає в шаблоні), нічого не редагуйте й не
   обходьте проблему. Поясніть користувачеві, що саме не працює і чому
   (`git -C <тека скіла> submodule status`, `ls -l` симлінка, документація у
   `vendor/`), і запропонуйте виправити встановлення та мігрувати на linerds,
   як описано вище.

## linerds (типовий)

Документація в `vendor/linerds/docs/`:

- `lab.md` — лабораторна чи практична від титулки до додатків;
- `coursework.md` — курсова робота й комплексний курсовий проєкт;
- `writing.md` — рисунки, таблиці, формули, код, посилання, джерела, додатки;
- `data.md` — усі поля `work(...)` / `doc.toml`, власні дисципліни;
- `reference.md` — перелік усіх функцій пакета.

Приклади в документації написано для mise з імпортом `@vendor/nure:0.3.0`.
Без mise (симлінк вище) імпортуйте `@local/nure:0.3.0`.

### Налаштування документа

Документ збирається з блоків. Дані роботи описуються один раз у `work(...)`, а
блоки беруть їх звідти:

```typst
#import "@local/nure:0.3.0": *

#let w = work(
  subject: "АПЗ", // скорочення, повна назва підставиться сама
  type: "ПЗ", // або "ЛБ", "КР", "ІДЗ" ("РФ" прибрано)
  number: 2,
  title: "Назва роботи",
  mentors: (
    (name: "Петренко П. П.", degree: "ст. викладач кафедри ПІ", gender: "m"), // m - чоловік, f - жінка
  ),
  authors: (
    (name: "Іваненко І. І.", edu-program: "ПЗПІ", group: "XX-X", gender: "m", variant: none),
  ),
)

#set document(..w.document)
#show: style.dstu.with(skip: 1) // титульна сторінка без номера

#report.title-page(w) // або report.title-page(w, layout: "complex")
#title-heading(w) // заголовок з темою; пропустіть, якщо не потрібен
#v(-style.spacing)
```

`work` перевіряє дані: у кожного автора обов'язкові `name` і `group`, у
кожного викладача — `name`, інакше звіт не скомпілюється. Не пропускайте ці
поля й не вигадуйте їх — спитайте в користувача.

Якщо поруч зі звітом лежить `doc.toml` з тими самими полями, замість переліку
аргументів можна написати `work(..toml("doc.toml"), title: "...")`.

### Що є лише в linerds

- `fig(path("img/a.png"), [Підпис], label: <a>)` — рисунок з приміткою про
  джерело. Шлях обов'язково обгортайте в `path()`: рядок шукався б у теці
  пакета. Звичайний `#figure(image(...))` теж працює.
- `tab(caption: [...], columns: 2, header: (...), ...)` — таблиця за ДСТУ;
  будь-яка `figure(table(...))` теж переноситься з «Продовження таблиці».
- `bib` / `dstu-bibliography` — перелік джерел за ДСТУ 3008:2015 або 8302:2015
  з файлу `bibl.yml`.
- `note[...]` / `dstu-note` — примітка за ДСТУ («Примітка. …», кілька
  нумеруються самі); до рисунка чи таблиці — параметр `note:` у `fig` / `tab`.
- `utils.noindent` — рядок без абзацного відступу, для пояснень «де …» під
  формулою.
- `style.dstu.with(section-numbering: false)` — наскрізна нумерація рисунків,
  таблиць, лістингів і формул («Рисунок 1» замість «Рисунок 1.1»).
- `report.title-page(w, layout: "nure-iki")` — титулка за рекомендаціями
  кафедри ІКІ (окрім `"default"` і `"complex"`).
- `work(city: "Київ")` — інше місто на титулці (`city: none` прибирає місто).
- Довгі лістинги (`figure(raw(...))`) і таблиці самі розриваються між
  сторінками з «Продовження …» / «Кінець …» — нічого додавати не треба.
- `docs/dstu.md` — таблиця, які пункти ДСТУ 3008:2015 реалізує шаблон.
- Курсові: `cw.*`, `cw-v2.*` або готові рецепти `coursework`, `coursework-v2`
  (див. `docs/coursework.md`).

## pencelheimer

Лише за прямим запитом. Підхід: `style.dstu` + глобальний `config.setup(...)`
+ блоки `parts.*`. Аргументи — у doc-коментарях `vendor/pencelheimer/src/config.typ`
і `src/parts.typ`, приклад — `examples/pencelheimer/example-pz.typ`.

## linerds_old (застарілий)

Застарілий шаблон (`linerds/typst_nure_template`, 0.1.x), більше не
оновлюється. Лише за прямим запитом або для підтримки наявних звітів на
`0.1.x`. Підхід: одна обгортка `#show: pz-lb.with(...)` (або `coursework`,
`coursework-v2`) з усіма аргументами. Сигнатури — у
`vendor/linerds_old/src/lib.typ`, приклад — `examples/linerds_old/example-pz.typ`.
Розділ README про Windows згадує функцію `nure-report` — такої в пакеті немає.
